# STEP 04: 로그인과 학생·관리자 권한 확인

이 단계는 사용자가 누구인지 확인하는 **인증**과, 로그인한 사용자가 무엇을 할 수
있는지 확인하는 **인가**를 구현합니다.

## 역할 구분

- `STUDENT`: 학생 화면, 플레이어 상태 조회, 본인의 신청곡 등록·조회
- `ADMIN`: 관리자 화면, 재생 제어, 신청곡 검토와 운영 설정 변경

학생이 관리자 주소나 제어 API를 직접 입력해도 서버가 `403`으로 거부합니다.
화면에서 버튼을 숨기는 것만으로는 보안이 되지 않으므로 모든 보호 API에서 역할을
다시 검사합니다.

## 로그인 흐름

1. 사용자가 이메일과 비밀번호를 입력합니다.
2. 서버는 DB에 저장된 Argon2 비밀번호 해시와 입력값을 비교합니다.
3. 성공하면 기존 세션을 비우고 새 사용자 ID와 CSRF 토큰을 저장합니다.
4. 브라우저에는 서명된 `jukebox_session` 쿠키가 전달됩니다.
5. 이후 요청마다 사용자가 존재하고 활성 상태인지 다시 확인합니다.

비밀번호 원문은 DB와 로그에 저장하지 않습니다. 존재하지 않는 이메일에도 가짜
해시 검증을 수행하고 동일한 오류 문구를 사용하여 계정 존재 여부를 추측하기 어렵게
합니다.

## 반복 로그인 실패 방어

동일한 접속 주소와 이메일에서 기본 5회 실패하면 5분 동안 추가 로그인을 `429`로
차단합니다. 비밀번호는 실패 기록에 저장하지 않습니다.

```env
LOGIN_MAX_ATTEMPTS=5
LOGIN_WINDOW_SECONDS=300
```

성공적으로 로그인하면 해당 실패 기록은 초기화됩니다. 이 제한기는 단일 앱 프로세스
기준입니다. 여러 서버를 동시에 운영할 때는 Redis 같은 공용 저장소로 교체해야 합니다.

## CSRF와 감사 로그

로그인 사용자가 재생 제어 같은 변경 요청을 보낼 때는 세션과 함께 발급된 CSRF
토큰도 필요합니다. 관리자의 중요한 변경은 `control_audit_logs`에 관리자 ID, 작업과
필요한 값이 저장됩니다.

## 자동 확인 항목

- 비로그인 사용자의 보호 API 접근은 `401`
- 학생의 관리자 화면과 제어 API 접근은 `403`
- 관리자의 학생 전용 화면 접근은 `403`
- CSRF 토큰 없는 변경 요청은 `403`
- 비활성 계정은 올바른 비밀번호여도 `401`
- 반복 로그인 실패는 `429`와 `Retry-After` 반환
- 로그아웃 후 기존 세션으로 다시 접근할 수 없음
